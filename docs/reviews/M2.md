# M2 Self-Review — Design System & Application Foundation

**Date:** 2026-07-12 · **Verdict: foundation is production-quality; proceed to M3.** Known debts are listed below with owners (a milestone) — nothing here is silent.

## What holds up

- **The contrast gate works as designed.** The palette was tuned _by the test_ — ~100 WCAG assertions across light/dark × normal/high-contrast, AAA for text in HC. This is the difference between "accessible palette" as a claim and as a property.
- **RTL is structural, not cosmetic.** Logical properties enforced by lint, sheet animations that flip with direction, direction-aware icon mirroring, and e2e that loads the Hebrew UI and asserts on real Hebrew copy. Switching to `/he` produces a native-feeling app, not a mirrored English one.
- **Consistency mechanisms are in place before scale arrives.** Tokens-only styling, semantic classes, one focus style, one motion vocabulary — the constraints that keep tool #400 looking like tool #4 exist before tool #1.
- **Verification is honest.** 26 turbo tasks + 13 e2e (palette flows, keyboard-only, contrast persistence) + 5 axe gates, all against production builds.

## Weaknesses found, and their disposition

1. **First-load JS is 191 kB — too close to the 200 kB budget.** The shell eagerly includes cmdk, several Radix trees, and both message catalogs. _Disposition:_ M3 adds a `size-limit` CI gate so the budget is enforced, not aspirational; palette becomes a lazy chunk prefetched on idle; client receives only the active locale's catalog. This is the top technical debt from M2.
2. **Palette search is cmdk's default filter, not the typo-tolerant index the architecture promises.** Fine for ~20 commands; not for 50+ tools. _Disposition:_ M4 introduces MiniSearch over `registry.search.ts` as designed — the palette's item model was kept registry-shaped so this is a data swap, not a rewrite.
3. **No pixel visual-regression baselines.** Deliberate (cross-env screenshot flake trains people to ignore CI), but it means visual drift in themes currently relies on Storybook review. _Disposition:_ dedicated consistent-rendering job planned alongside M9 ops work; recorded in 05 §6.
4. **Theme/contrast controls render only after mount** to avoid hydration mismatch — a brief empty slot in the settings rows and menus on slow devices. Standard next-themes cost; acceptable, revisit only if users notice.
5. **e2e is Chromium-only** and single-viewport per test. _Disposition:_ add WebKit + a mobile viewport project when the file-drop surfaces land (M5) — that's when engine differences start to matter.
6. **Toasts are mounted but unused**, and category pages are intentional placeholders. Not debt — staging. They exist so M3/M4 land into working sockets.
7. **Storybook stories are grouped by domain** rather than per component. Right-sized at 27 components; split as the library grows (noted in the ui README).

## Bugs caught by this milestone's own gates (evidence the gates earn their keep)

- `CommandDialog` originally rendered cmdk children without the `Command` root — a guaranteed runtime crash, caught by e2e before any commit shipped.
- Missing direct deps (`lucide-react` in web, `@omnio/core` in i18n tests) — caught by pnpm isolation + vitest, fixed by declaring reality.
- A build/typecheck race on `.next/types` — fixed structurally in the turbo graph (typecheck now depends on own-package build), not by retrying.

## Architecture confirmations

No regrets on: tokens-in-TypeScript with generated CSS (the codegen + drift-test loop is frictionless), contrast as an axis instead of a theme, CSS-only motion (nothing yet missed Framer), shipping ui as source, build-time i18n catalogs with parity tests. The M1 decision to keep NestJS/ts-rest untouched by M2 also proved out — zero backend churn this milestone.
