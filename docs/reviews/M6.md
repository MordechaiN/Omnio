# M6 Self-Review — First End-to-End Journey

**Date:** 2026-07-17 · **Verdict: Omnio is now a product, not a shell around tools. A visitor can go from a blank instance to a processed, re-downloadable file without ever touching a terminal — and every screen on that path is one I'd show on Product Hunt.** Debts carry an owner.

## What holds up

- **The front door is complete.** First run shows a branded setup screen (single-admin, decision D2); returning visitors get login; an unreachable API shows an honest offline-retry state; only an authenticated session reaches the workspace. The gate wraps the app behind a splash so there is no flash of private UI.
- **The journey is real, not mocked.** Drop or choose a file → it uploads (raw multipart), enqueues a worker job, and streams live progress over SSE into a global **Activity** tray that resolves to a download. Browser-tier tools keep their on-device UI; anything server-side now has a first-class client runtime. One tracked entry per run, from `uploading` through a terminal state.
- **Results persist.** `GET /api/v1/jobs` backs a History page — every run the account has enqueued, newest first, with status and a download for each output. Finishing a run invalidates the history query, so the tray and History stay in sync live.
- **States and polish everywhere.** Loading skeletons, error+retry, empty states, toasts on completion/failure, tray row enter animations, and logical-property layout that stays correct in RTL with zero extra work.
- **Accessibility is gated, not hoped for.** The full Playwright suite (24 tests) is green, including axe over the open Activity tray and the History surface — which surfaced and fixed real `aria-progressbar-name` and file-input `label` violations before they shipped.

## Weaknesses found, and their disposition

1. **No runtime end-to-end here.** No DB/Redis in this environment, so the upload→worker→SSE path is proven by types, unit/e2e with a mocked API, and the existing Testcontainers CI — not by a live round-trip in this session. _Disposition:_ CI exercises the real services; owner **CI**.
2. **Drop→action-sheet still has no synthetic e2e.** Driving native drag-and-drop in Playwright remains awkward; the worker-run path is instead covered end-to-end via the tool-page launcher (upload→SSE→download). _Disposition:_ carry the synthetic drop test forward; owner **M7**.
3. **History shows tool + status + download, not input/output filenames.** File names would need a `files` join or per-id metadata fetch. _Disposition:_ additive when a run detail view lands; owner **M7+**.
4. **Cross-origin SSE depends on `OMNIO_ALLOWED_ORIGINS`.** `EventSource(withCredentials)` needs the api's CORS to name the web origin — correct by config, but a same-origin reverse-proxy deployment is the smoother default. _Disposition:_ documented; owner **M9 (ops)**.

## Architecture confirmations

No regrets on: the typed ts-rest client as the single web↔api contract; a client-side job runtime (context + tray) rather than a store dependency, so the whole app sees runs without prop-drilling; relaying the worker's Redis progress channel over SSE (server→client, proxy-friendly) instead of polling; and keeping module surfaces decoupled — the app owns `runJob`, so worker tools never import app internals. The universal file viewer flagship was resequenced (see [../architecture/07-roadmap.md](../architecture/07-roadmap.md) M6); the M5 viewer foundation already covers on-device preview, so nothing regressed by waiting.
