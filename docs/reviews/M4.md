# M4 Self-Review — Module System

**Date:** 2026-07-17 · **Verdict: the module system holds; the platform can now grow by modules, not core edits. Proceed to M5.** Debts below carry a milestone owner.

## What holds up

- **Zero-registration discovery is real.** Creating a module folder and running `pnpm modgen` (which Turbo runs before every build/typecheck/dev) makes the tool appear — the `uuid` tool prerenders at `/en/tool/uuid/uuid` and `/he/tool/uuid/uuid`, code-split, listed in the palette, with no import or registry file edited by hand. modgen also keeps each app's `@omnio/mod-*` dependencies and the Next transpile list in sync.
- **Manifest violations fail the build with actionable errors.** The SDK Zod schema (tierReason above browser tier, unique tool ids, fileAction references, i18nNamespace convention) plus modgen's category-membership, dead-surface, and en/he i18n completeness+parity checks — each error names the module and the fix. Generated output is a build artifact (gitignored, lint/format-excluded).
- **The three tiers share one contract.** `@omnio/module-sdk` (MIT, dependency-free of the AGPL core) defines `BrowserTool`/`ServerTool`/`WorkerTool`, options-as-Zod, and `ctx.exec()`. The worker runs registry tools through it end to end: isolated per-job scratch dir, inputs staged in, outputs persisted out, progress mirrored to Postgres and SSE, and a real sandboxed `exec()` (argv-only, scrubbed env, timeout+output cap, unit-tested).
- **Consistency is structural.** Every surface renders inside `ToolShell`; every module string is an i18n key merged under its namespace at build; every worker subprocess goes through `ctx.exec()`. Scaffolders (`pnpm new:module` / `new:tool`) emit skeletons that pass modgen unchanged.

## Weaknesses found, and their disposition

1. **The server tier is deferred.** There is no server reference module yet, so the api's generated registry is empty and imports nothing — the backend is untouched. _Disposition:_ the first real server tool (M7/M8) brings the api onto NodeNext resolution the same way the worker moved, and adds the reference module then. Documented rather than stubbed with dead code.
2. **The worker moved to NodeNext ESM and bundles with tsup.** Module worker-tier code ships as TypeScript source, so the worker bundles it (runtime libs stay external) into one runnable artifact — which also serves M9's image story. _Disposition:_ intentional; the api will follow when it gains server modules.
3. **Palette search is cmdk's built-in filter over name+keywords, not the MiniSearch typo-tolerant index** the M2 review earmarked for M4. _Disposition:_ fine at two tools; the entries are already registry-shaped, so MiniSearch is a data swap when the catalog grows (M7).
4. **Worker-tier surfaces are placeholders.** They prove discovery + the execution path; the upload → enqueue → progress → download UX is the file-action flow and jobs tray in M5. Not debt — sequencing.
5. **Tool icons resolve by name via lucide `DynamicIcon`.** Convenient and per-route, but each tool route pays a small dynamic-import cost. Revisit only if a route's budget bites.

## Architecture confirmations

No regrets on: registries-as-data (nothing in core assumes modules are compiled in — the worker proves the registry is just a map), build-time discovery over runtime scanning, the SDK published MIT and free of the category list (so the manifest schema carries no AGPL dependency), and merging module i18n namespaces at build. The manifest is genuinely the module's whole public identity — the file-drop `capabilities.json`, search index, and input validation all read the same declaration.
