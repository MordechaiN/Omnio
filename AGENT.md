# AGENT.md — Operating Manual for AI Sessions

This file is the primary instruction set for every AI session working in this
repository. Read it first, follow it always. It defines **how to work here** —
not what to build. Product vision, architecture, and the roadmap live in
[`docs/`](docs/) and are not repeated here.

If anything below conflicts with a direct instruction from the maintainer, the
maintainer wins for that session; this manual governs everything else.

---

## Repository Philosophy

- **The repository is the single source of truth.** Code, `docs/architecture/*`,
  and `docs/reviews/*` are authoritative. Trust them over memory or assumption.
- **Approved architecture is binding.** Decisions in `docs/architecture/08-decisions.md`
  and the architecture package are settled. Build on them.
- **Completed milestones are stable.** Anything marked ✅ in
  `docs/architecture/07-roadmap.md` is done. Do not redesign it.
- **Change completed work only for a critical flaw** — a correctness, security,
  or data-integrity defect. Cosmetic or stylistic dissatisfaction is not a
  reason. When a real flaw is found, stop and flag it before reworking.

---

## Working Style

Work like a senior staff engineer maintaining a mature production codebase.

- Prefer implementation over narration; prefer writing code over explaining it.
- Think carefully **once**, then: **implement → verify → commit → continue.**
- Avoid perfection loops, speculative refactors, and rewriting working code.
- Avoid long internal analysis. When a production-quality path is clear, take it.
- Leave the code better than you found it, without gold-plating.

---

## Session Startup

On every new session:

1. Read this `AGENT.md`.
2. Determine the latest completed milestone from `docs/architecture/07-roadmap.md`
   (last ✅) and skim its review in `docs/reviews/`.
3. Read **only** the documents needed for the current task.
4. Continue implementation of the next milestone/slice.

Do not rescan the repository, restart planning, regenerate architecture
documents, or re-derive context that already exists.

---

## Repository Navigation

- Open known files directly; do not recursively scan or repeatedly index the tree.
- Read only files directly related to the current task.
- Trust architecture docs and milestone reviews instead of re-reading everything.
- Avoid expensive repo-wide searches for orientation. Targeted search for a
  specific symbol is fine; sweeping the codebase to "understand the project" is not.

---

## Token Efficiency

Tokens are spent building features, not describing them.

- Never summarize completed milestones or restate the roadmap.
- Never re-explain architecture that already exists in `docs/`.
- Don't repeat information already established in the session or the repo.
- Keep reasoning concise and decision-focused.

## Development Workflow

Implement in **small vertical slices**. Complete one subsystem, verify it, commit
it, move on. Each slice must:

- compile
- pass affected lint
- pass affected typecheck
- pass affected tests

Run **full-repository verification only when a milestone is complete** (or the
maintainer asks). Do not batch large amounts of unrelated change into one slice.

---

## Testing Policy

Use the smallest verification that gives real confidence.

- Run only the affected packages' lint/typecheck/tests (`pnpm --filter <pkg> …`
  or `pnpm turbo <task> --filter=<pkg>`).
- Avoid full monorepo builds after every change.
- Run Playwright only when a change actually affects a browser flow.
- Avoid unnecessary dependency installs and repeated dependency resolution.
- Do not re-run verification that has already passed unchanged.
- `modgen`-generated files under `apps/*/src/generated/` are build artifacts:
  gitignored, regenerated by the `codegen` Turbo task before build/typecheck.
  Never hand-edit them.

---

## Git Workflow

Single maintainer. **The AI owns all Git operations; the maintainer performs none.**

- Work directly on `main`. Keep `main` production-ready at all times — never
  leave it broken.
- Push to `origin/main` after each completed vertical slice, once it compiles
  and affected tests pass.
- Make small, logical commits with clear messages describing intent.
- If a change is genuinely risky or experimental, create a temporary branch,
  validate it fully, merge/fast-forward it back into `main`, push, and delete
  the branch — all without maintainer involvement.
- Maintain a clean, linear history. Never ask the maintainer to merge, rebase,
  cherry-pick, or resolve conflicts. Resolve them yourself.
- Commit-message trailers and any harness-mandated conventions still apply.

---

## Code Review (before every commit)

Review your own diff before committing. Look for and fix:

- simplification opportunities and unnecessary complexity
- duplication (extract or reuse instead)
- weak or misleading names
- readability gaps

Only commit once the diff is clean. This is a quality pass, not a bug hunt —
verification covers correctness.

## Documentation Policy

- Update docs only when an implementation change requires it (new/changed
  behavior, config, or milestone status).
- Do not rewrite documentation for style, and do not duplicate it.
- Milestone completion: mark the roadmap ✅ and add a concise `docs/reviews/M<n>.md`.

## Communication Style

Keep reports concise. The default completion report is **≤10 lines** and contains
only:

- **Implemented** — what changed, in one or two lines
- **Files changed** — the notable paths
- **Tests executed** — what was run and the result
- **Blockers** — anything unresolved, or "none"

Expand only when the maintainer explicitly asks for more detail.

## Engineering Principles

Non-negotiable defaults for all code:

- Long-term maintainability over short-term speed
- Modularity and respect for module boundaries
- Strong typing (no `any`-escapes without cause)
- Security, accessibility, performance, and privacy **by default**
- Docker-first, self-hosted-first
- No technical debt, no placeholder implementations, no hacks
- No unnecessary abstractions, no duplication

Production quality is the floor, not the goal.

### A file has exactly one understanding

`packages/workspace/src/insights.ts` is the only place in Omnio that decides
what a file *is*. Everything that needs to know something about a file — the
drop panel, the Inspector, Discoveries, Quick Look, search, any tool surface —
asks that engine. Screens present the understanding; they never compute it.

This is not a style preference. Omnio previously kept a second set of
heuristics for the drop panel, and the two disagreed: the same photo was
"large, compress it" on one screen and unremarkable on another, while
screenshots and scans were invisible to one side and oversized PDFs invisible
to the other. Every such split is a future bug that no test will catch, because
each half passes its own tests.

Therefore:

- A new capability that needs a fact about a file **extends the engine**. It
  does not read the bytes again on its own.
- A new fact about a file belongs in `FileFacts`, in the workspace's
  vocabulary, whatever discovered it.
- Two parts of Omnio must never learn the same fact independently.
- If a surface needs to say something the engine cannot express, the fix is to
  teach the engine, not to add a special case beside it.

Adding a heuristic outside this engine is a defect, however small it looks.

### Omnio owns ports 7400–7449 and uses nothing else

Every port Omnio binds comes from that range: web `7400`, api `7410`, worker
health `7420`, and in dev postgres `7432`, redis `7479`. Full table and
reasoning: `docs/ports.md`.

The popular defaults are shared property. Taking 3000 or 5432 means a developer
cannot run Omnio and their other project at the same time without editing config
first — a permanent cost to everyone, to save a few characters once.

Therefore:

- A new service takes the next free number in the range. Never a familiar
  default, and never something inside the ephemeral range (32768–60999), where
  the kernel may have handed the port out already.
- One number per role, everywhere: dev command, container, health check,
  Dockerfile, docs. A deployment may republish on a different *host* port via
  `WEB_PORT`/`API_PORT`; the port inside the container is fixed so the two can
  never disagree.
- `scripts/check-ports.sh` must stay in step with `docs/ports.md`.

## Decision Making

- If an obvious production-quality solution exists, implement it. Do not survey
  multiple approaches for its own sake.
- Ask the maintainer **only** when a decision materially changes the architecture
  or product direction, or when required inputs are genuinely missing.
- Otherwise, pick the sensible default, note it briefly, and keep working.
